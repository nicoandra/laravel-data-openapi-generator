# Reject non-string cast input before verification

## Objective
Close the input-shape bypass where an attacker submits an array or object for a field expected to contain a signed token.


## Human developer notes
This task is a tricky one. We use Laravel-Data, when we POST an array, Laravel-Data would normally detect we're building the Cursor from an array, and might just build it. So we need to be creative on how we can "inject" our code before the instantiation. We could use traits to inject a custom `static from()` method, or we can add a signature __inside__ the object properties that we'll validate using `pipelines`.

I think we might want to create our own `SignedData extends Data` and provide it as a tool for developers to use it instead of using `Data` directly. There are different options, we need to identify a good approach to avoid the creation of instances through an array when being POSTed.

## Expected outcome
The cast boundary validates that the incoming value is an allowed encoded-string representation before any hydration occurs. Arrays, objects, and other non-string values cannot be passed into Laravel Data hydration as trusted field data. The failure behavior is explicit and consistent with the package's validation/error conventions.

The design should also consider whether strict string checks belong in the cast, the codec, or both, while ensuring signature verification remains mandatory for every accepted token.



## Evaluation
Regression tests submit arrays and objects containing attacker-controlled fields and prove that the target Data object is not hydrated from them. Tests also cover scalar non-strings, valid strings, malformed encoded strings, and valid signed tokens. The full cast integration suite passes, and the rejection occurs before any attacker-controlled value can bypass signature verification.
